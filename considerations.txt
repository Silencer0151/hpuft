The default output should be clean, actionable, and human-readable (like wget or rsync). But when you flip a --debug switch, it should dump the raw protocol state machine data you need to diagnose a LFN (Long Fat Network) collapse.

Here is the exact UX and logging specification for the three commands in your fat binary.
1. Global Logging Principles

    Standard Out vs. Standard Error: All interactive progress bars and human-readable summaries go to stdout. All debug logs, warnings, and errors go to stderr. This ensures that if someone scripts hpuft get target.tar.gz > target.tar.gz, the file data doesn't get corrupted by log text.

    The "In-Place" Progress Bar: For active transfers (push and get), the terminal should not scroll endlessly with log lines. It should use carriage returns (\r) to overwrite a single, highly dense status line at the bottom of the terminal.

2. Command: serve (The Daemon)

Who is watching: Usually no one. It runs in the background or inside a tmux session.
Behavior: It should be completely silent until a discrete event happens. It does not show a live progress bar, because a server shouldn't waste CPU cycles drawing CLI graphics.

    Startup:
    [serve] Online. Listening on 0.0.0.0:9000
    [serve] Manifest loaded: 14 authorized files found in ./shared_folder

    Event: Connection Rejected (Security/Busy):
    [serve] REJECTED 198.51.100.4: PULL_REQ for 'shadow' (Not in manifest)
    [serve] REJECTED 203.0.113.8: SERVER_BUSY (Transferring to 198.51.100.4)

    Event: Successful Transfer (Acts as Sender):
    [serve] ACCEPTED 198.51.100.4: PULL_REQ for 'darksouls3_2022.09.05.mp4'
    [serve] TRANSFER COMPLETE: 'darksouls3_2022.09.05.mp4' to 198.51.100.4 in 2.1s (110.4 MB/s)

3. Command: push (The Client Sender)

Who is watching: The user actively sending a file.
Behavior: Needs to show the handshake establishing, and then provide a live look into the Congestion Control (CC) engine's performance.

Default Output Sequence:
Plaintext

[push] Target: darksouls3_2022.09.05.mp4 (232 MB)
[push] Hash computed: 0x2681C51BDEAEBA6F
[push] Sending SESSION_REQ to 198.51.100.4:9000 (SessionID: 0xF4CFD01D)
[push] Handshake accepted. Calibration train (10 pkts) dispatched.

darksouls3...mp4 [=======>          ]  45% | 115.2 MB/s | ETA: 00:01 | FEC: 5% | NACKs: 0

Notice the progress bar: It shows the exact metrics the sender cares about.

    MB/s: The current EWMA smoothed delivery rate.

    FEC: The current dynamic parity ratio.

    NACKs: Total NACKs the sender has had to retransmit.

Teardown Output:
Plaintext

[push] EOF sent. Waiting for remote hash verification...
[push] TRANSFER COMPLETE received. Linger state finished.

4. Command: get (The Client Receiver)

Who is watching: The user actively downloading a file through the NAT hole.
Behavior: It needs to confirm the NAT punch worked, show memory allocation, and provide a live look into the Receiver's flush rate and FEC recovery.

Default Output Sequence:
Plaintext

[get] Punching NAT hole via PULL_REQ for 'darksouls3_2022.09.05.mp4' -> 198.51.100.4:9000
[get] Received SESSION_REQ. Allocating 232 MB ring buffer...

darksouls3...mp4 [=======>          ]  45% | 115.2 MB/s | ETA: 00:01 | Rebuilt: 14 pkts

Notice the progress bar differences: The receiver doesn't care about NACKs sent; it cares about Rebuilt.

    Rebuilt: How many missing packets the Reed-Solomon math successfully reconstructed on the fly without having to ask the sender for a NACK. This proves the UDP engine is doing its job.

Teardown Output:
Plaintext

[get] EOF received. Flushed to disk.
[get] Local Hash: 0x2681C51BDEAEBA6F | Remote Hash: 0x2681C51BDEAEBA6F
[get] Hash MATCH. Transfer successful.

5. The --debug Flag (Under the Hood)

When you are testing your custom protocol algorithms, the progress bar gets suppressed and the terminal streams the raw telemetry.

If you append --debug to push or serve, you should see the exact decisions your CUBIC-style engine is making:

[cc_debug] RTT: 32ms | Dispersion: 1.24 MB/s | Phase: 1 (Probe)
[cc_debug] HEARTBEAT received: Delivery: 98.4 MB/s | Loss: 0.00%
[cc_debug] INCREASE (1.25x): Target rate updated to 123.0 MB/s
[cc_debug] HEARTBEAT received: Delivery: 112.1 MB/s | Loss: 1.50%
[cc_debug] HOLD (Loss zone entered). Phase 1 terminated. Entering Phase 2 (Additive).
[cc_debug] Parity ratio dynamically adjusted to 5% (Block size: 100)


Below is a breakdown as to what is currently happening:
1. Verbosity Bleed (The --debug Requirement)

What's Happening: Your congestion controller is vomiting its state changes ([congestion] INCREASE..., [sender] queued 167 new NACKs...) directly into standard output by default.
The Correction: All of these log.Printf statements inside congestion.go and the NACK queues in sender.go need to be hidden behind a --debug flag. Normal users do not want to see 40 lines of [congestion] INCREASE (phase1) before their file finishes. The default output should be near-silent until the transfer completes.
2. serve is Leaking sender Logs

What's Happening: When your serve daemon accepts the PULL_REQ for the Dark Souls mp4, it correctly prints [serve] serving.... But immediately after, the underlying sender goroutine dumps its entire initialization, hashing, and congestion control sequence to the screen.
The Correction: serve needs to be able to instantiate the Sender with a "quiet mode" toggle. When running as a daemon, serve should suppress all [sender] logs and only print the start and end of the transfer.
3. The Missing In-Place Progress Bar

What's Happening: Instead of a clean, overwriting progress bar, the sender is printing new lines every 10%: [sender] progress: 10%..., [sender] progress: 20%.... The receiver (get command) is printing nothing at all between buffer allocation and finalization.
The Correction: We need to implement a carriage return (\r) print loop. This will anchor a single line to the bottom of the terminal that updates in real-time.

    For send / push: It should display a single updating line showing [=========>   ] 45% | 115 MB/s | NACKs: 8.

    For get / recv: It should display [=========>   ] 45% | 115 MB/s | FEC Rebuilt: 0.

4. Splitting stdout and stderr

What's Happening: Right now, everything appears to be coming through Go's default log package, which writes to stderr with a timestamp prefix (12:41:15.112571).
The Correction: To be scriptable (like rsync), standard user output (like the progress bar or final completion message) should go to os.Stdout without timestamp prefixes. Diagnostic logs (when --debug is active) should stay on os.Stderr with the timestamps.

================================================================================
  SINGLE-PORT SINGLE-SOCKET: THE SIMPLE APPROACH
================================================================================

THE KEY INSIGHT
---------------
We are single-lane. Exactly one transfer runs at a time. The serve daemon
already knows whether it is in PULL mode or PUSH mode because it set busy=1
when it accepted the request. So the control loop does not need session ID
routing, packet type inspection, or SO_REUSEPORT tricks. It just needs to ask:

  "Am I busy right now?"
  - No  -> dispatch PULL_REQ / PUSH_REQ as normal
  - Yes -> forward this raw packet to whoever is active

That's it. One socket on one port. The active goroutine decodes its own packets.


CONCRETE IMPLEMENTATION
------------------------
1. Add  activeChan chan []byte  to the serve state.
   Buffered (e.g. 256 slots) so a burst of packets doesn't stall the loop.

2. Main read loop changes from:

     switch pkt.Header.Type {
     case PacketPullReq:  handlePullReq(...)
     case PacketPushReq:  handlePushReq(...)
     }

   to:

     if atomic.LoadInt32(&busy) == 1 {
         // Clone the bytes and forward; main loop reuses rawBuf.
         pkt := make([]byte, n)
         copy(pkt, rawBuf[:n])
         select {
         case activeChan <- pkt:
         default: // channel full: drop, sender/receiver will NACK/retransmit
         }
         continue
     }
     switch pkt.Header.Type { ... }  // same as before

3. sender.Config gets two optional fields:
     WriteConn    *net.UDPConn   // shared control conn for sends
     WriteAddr    *net.UDPAddr   // parsed client address for WriteToUDP
     RecvChan     <-chan []byte  // channel to read packets from

   When these are set, Send() skips net.DialUDP and uses them instead.
   All conn.Write(raw) calls become conn.WriteToUDP(raw, WriteAddr).
   The heartbeat/NACK read loop does:
     buf := <-RecvChan  instead of  conn.Read(buf)

4. receiver.Config already has Conn. Add:
     RecvChan  <-chan []byte

   Run() reads from RecvChan when set, conn.ReadFromUDP otherwise.
   Heartbeat writes go to conn.WriteToUDP(raw, senderAddr) — same as now.

5. serve.go handlePullReq / handlePushReq: create activeChan, pass
   WriteConn/WriteAddr/RecvChan to sender, pass Conn/RecvChan to receiver.
   No new sockets bound anywhere.


WHAT THIS ELIMINATES
---------------------
- The -data port flag entirely
- The PULL_ACCEPT packet type (0x0A) and its protocol machinery
- The 200ms sleep before the sender goroutine starts
- The probe packet logic in get.go
- The second router port-forward rule

The client just sends PULL_REQ to port 9001. SESSION_REQ comes back from port
9001. All data flows through port 9001. The NAT hole punched by PULL_REQ covers
everything because there is only one port.


HOW THE STANDALONE COMMANDS ARE UNAFFECTED
-------------------------------------------
send / recv / push / get do NOT set WriteConn / WriteAddr / RecvChan.
Sender and receiver detect nil values and fall back to the current DialUDP /
ListenUDP socket ownership paths. Zero behaviour change for those commands.


COMPLEXITY ESTIMATE
--------------------
Sender changes:
  - Add 3 fields to Config.
  - Wrap the DialUDP block: if WriteConn != nil { use it } else { dial as now }.
  - Replace conn.Write(raw) with a small helper:
      func (s *Sender) write(conn *net.UDPConn, raw []byte) error
    that calls conn.Write or conn.WriteToUDP(raw, s.cfg.WriteAddr) depending
    on which mode is active. This helper is called at ~5 sites.
  - In the heartbeat goroutine, replace the conn.Read loop with a select over
    RecvChan and a done signal.

Receiver changes:
  - Add RecvChan <-chan []byte to Config.
  - In Run(), the inner read becomes:
      if r.cfg.RecvChan != nil { buf = <-r.cfg.RecvChan }
      else { n, addr, err = r.conn.ReadFromUDP(rawBuf) }

Serve changes:
  - activeChan creation and cleanup (set to nil after busy clears).
  - Forward block in main loop (~8 lines).
  - Pass the fields in handlePullReq / handlePushReq.

Total: roughly 60-80 lines changed across three files. No new protocol packets.
No platform-specific code. No new dependencies.


VERDICT
--------
This is the right approach. The 2-port model should be treated as a stopgap.
Once this is implemented:
  - 1 port to forward
  - Simpler protocol (no PULL_ACCEPT, no probe, no sleep)
  - Serves as a natural stepping stone toward the Phase 2 C mux architecture
